# Explanatory writing: turning material into notes you can learn from

This applies whenever the main goal is **understanding**: rewriting course slides or a
course PDF, explaining a paper in detail, recapping documentation, or writing about a
topic with no source at all. The reader wants to understand *why* things are true, not
just collect statements, and usually learns well from pictures.

## Principles

1. **Plain language first, formal statement second.** Write as if for a smart friend who
   has forgotten the topic. Then give the precise version in an `nbdef`/`nbfact`.
2. **Explain every formula.** Say what each symbol means, why each condition is there,
   and what would break without it. A formula without commentary is a gap.
3. **Never skip steps.** No "it follows that X becomes Y". Show every intermediate line,
   especially in examples and exercises, and annotate non-obvious steps (`\reason{}`).
4. **Intuition throughout.** Each important idea gets an analogy, a geometric picture or
   a "what is this really saying" box, placed where it helps the formal part land.
5. **Concrete before and after abstract.** After a definition, a small example with real
   numbers; then back to the general case.
6. **Draw it.** Add a figure whenever a picture explains faster than prose: geometry,
   shapes of functions, transformations, distributions, algorithms as diagrams. Not every
   formula needs one; when in doubt, draw it.
7. **Connect.** Link to earlier sections (`\ref`), to applications in the reader's field
   (`nbwhy`), and between examples ("this is the same system as Exercise 1.9").
8. **Anticipate mistakes.** Put the classic traps in `nbwarning` boxes.

## Working from a source (slides, PDF, paper, docs)

- **Read the whole source first** (in page ranges if it is long) and plan the mapping:
  usually one source chapter = one sub-section folder, in the same order.
- **Cover everything** in the source, then add what helps (missing steps, intuitions,
  pictures, sanity checks). Do not silently drop items.
- **Keep the source's numbering** (Def. 2.1, Exercise 4.7) in box titles, so the notes can
  be read side by side with the original.
- **Fix the source, do not copy its errors.** Course material has typos and shortcuts.
  When something is wrong or incomplete, write the correct version and add an
  `nbwarning` explaining the difference ("the slides write ..., but ..."). Examples met in
  practice: an angle range given as [0, 2π) where arccos returns [0, π]; `θ = arctan(b/a)`
  stated without the quadrant correction; a heuristic presented as a proof; an exercise
  claiming an exact result that only holds to first order.
- **Exercises get full solutions** (in `nbsolution`), even if the source has none. End a
  solution with a short "Lesson" or interpretation when it teaches something general.
- **Check the numbers.** Before writing any numerical result (eigenvalues, an SVD, an
  integral, a probability table), verify it with a quick script (numpy/sympy/fractions).
  End worked examples with a check (rebuild the matrix, substitute back, compare with a
  second method).

## Explaining a paper

- Start with the problem the paper solves and why previous approaches were not enough,
  before any method details.
- Build up the notation the paper uses, defining each symbol at first use, then follow
  the paper's derivations and fill in the steps it skips ("it is easy to show that").
- Give each main equation its own intuition and, where possible, a toy numerical example.
- Separate clearly what the paper claims, what is proved, and what is only shown
  empirically. Add your own `nbwarning` when an assumption is strong or easy to miss.
- End with a summary of contributions and the limitations you noticed.

## Writing without a source

- Define the scope first (a short numbered list "this section covers"), then build from
  the simplest case to the general one.
- Use the same box vocabulary and the same verification discipline; the lack of a
  source makes checking the math more important, not less.

## Structure of a section

1. `\subsection{...}` + `\label{...}`, then a short intro: why the topic matters and a
   numbered list of what the section covers.
2. Theory in `\subsubsection`s, in a logical (or source) order.
3. `\subsubsection{Exercises}` with `nbexercise` + `nbsolution` pairs, if there are any.
4. A closing `nbsummary` cheat sheet: the handful of formulas and facts to remember.

## What the reader must never see

The PDF is for studying. Keep repository internals out of the visible text: no file
paths, script names, `.tex`/`.py` names, macro or toggle names, "generated by ...", "see
assets/...". That information belongs in `AGENTS.md`, code comments or commit messages.
Code listings that are part of the material (e.g. an exercise asking to run code) are
fine, but strip comments that only describe how to run the file inside the repo.

## Pacing a large job

For long sources, write and verify one chapter at a time. Show the user the first
chapter (compiled) early if the style is new to them, since feedback on depth and tone
is cheap to apply then and expensive later.
